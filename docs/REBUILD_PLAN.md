# A 股量化研究平台项目手册

## overview

这是一个面向 A 股日频研究的轻量量化平台。系统从 2025-01-01 开始维护研究数据，以 PostgreSQL 16 为唯一主库，以 Tushare Replay 为唯一外部数据平台。网站只提供研究、回测、模拟组合和运维观测，不开放公网写操作，也不承担实盘交易。

当前版本采用完全重构路线，不兼容旧页面和旧采集程序。核心目标是把“数据是否可信、信号如何产生、回测能否复现、组合现在怎样”放进同一条可追溯工作流，而不是堆叠彼此孤立的行情页面。

> 生产地址：`http://140.245.53.52:8080/`　API 前缀：`/api/v1`　文档锚点：`/docs.html#overview`

## product-design

### 产品定位

平台的第一使用者是做 A 股事件与人气研究的个人研究员。信息架构按研究动作划分，而非按后端表名划分：

| 页面 | 要回答的问题 | 主要数据 |
|---|---|---|
| 总览 | 数据是否就绪，今天从哪里开始研究？ | 覆盖率、研究流水线、重点入口 |
| 人气研究 | 哪些股票受到关注，排名如何在盘中变化？ | 东方财富 Top100 全时点快照 |
| 龙虎榜 | 哪些股票上榜，资金来自哪些席位？ | `top_list`、`top_inst` |
| 策略实验 | 这组参数在固定数据版本上表现如何？ | 实验、信号、成交、指标 |
| 模拟组合 | 策略进入连续交易日后仓位与风险如何？ | 现金、持仓、订单、净值 |
| 系统状态 | 数据是否完整，哪个批次需要处理？ | 回补进度、批次、任务状态 |
| 资金流 | 哪些个股或板块连续获得主力净流入？ | 东财个股与板块资金流 |

### 设计参考与取舍

设计借鉴开源量化项目的成熟概念，但不直接复制其代码或品牌视觉：

- Microsoft Qlib：采用“数据、模型/信号、回测、线上服务”的研究工作流分层，以及实验可复现的理念。
- QuantConnect LEAN：采用模块可替换、研究项目与运行结果分离的组织方式。
- VeighNa：借鉴交易终端的信息密度、状态可见性和事件驱动模块边界。
- Freqtrade：借鉴回测记录、参数比较、模拟运行与绩效面板的任务导向设计。

界面使用深色研究终端风格，但通过清晰层级、留白、状态色和响应式布局控制认知负担。红色表示上涨、绿色表示下跌，遵循 A 股用户习惯；系统成功状态使用青绿色，告警使用琥珀色，避免与行情涨跌混淆。

### 页面交互原则

1. 先显示数据时间与来源，再显示结论；用户必须知道结果对应哪个交易日。
2. 总览只展示可行动的指标，详细批次进入系统状态页。
3. 表格承担精确比较，图表承担趋势识别，不为装饰重复同一信息。
4. 龙虎榜使用主从结构：左侧个股榜单，右侧下钻营业部/机构席位。
5. 缺少后端指标时明确显示“待计算”，不使用看似真实的随机模拟值。
6. 桌面端保持高信息密度；移动端收起侧栏为底部导航，核心查询仍可完成。

### 龙虎榜页面原型 V1

![龙虎榜页面高保真原型 V1](/docs/lhb-prototype-v1.png)

原型采用单一全局导航：左侧栏负责六个一级模块，顶部栏只承担面包屑、全局股票搜索、交易日和文档入口，不再重复出现一级页面按钮。龙虎榜主体采用“榜单 + 个股详情”主从结构：左侧完成全市场扫描，右侧完成席位、历史上榜与资金趋势下钻。

页面必须直接展示席位覆盖状态。完整时显示绿色状态；上游只返回部分席位时显示琥珀色“席位数据不完整”，并说明缺少的是普通营业部还是全部席位，不能让空表看起来像当日没有交易。

此原型参考[涨停客每日龙虎榜](https://zhangtingke.com/lhb_date)的日期直达、密集榜单、题材与原因同屏等信息组织方式，但保留本平台的数据审计、席位下钻和研究终端结构。

### 龙虎榜页面原型 V2：加入个股资金流

![龙虎榜页面原型 V2：个股资金流](/docs/lhb-prototype-v2-moneyflow.png)

## concepts

### 交易日与信号时点

所有策略遵循无未来函数原则：T 日收盘后才能使用 T 日完整数据产生信号，最早在 T+1 日开盘成交。回测和模拟组合都使用相同语义，避免研究结果与实际执行口径不一致。

### 人气 Top100 与最终榜单

系统同时调用 `dc_hot`（东方财富）与 `ths_hot`（同花顺）历史接口，使用 `is_new=Y` 只保存每个交易日的最终 Top100。两个接口的页面与 API 均以 `source` 参数隔离，明确显示中文来源及接口标识；不合并、不相互补位。该口径不代表全市场全部股票，也不再采集盘中全时段快照。

若 Replay 明确缺少某日最终榜单，则标记为 `unavailable`，绝不使用另一来源冒充或伪造记录。每个来源的缺档状态独立监控。

### 龙虎榜

`top_list` 保存上榜证券、涨跌幅、成交额、换手率和上榜原因；`top_inst` 保存买卖营业部或机构席位。金额统一换算为人民币元。页面按“交易日 + 股票”关联两类数据，当个股汇总净额为空时，可依据席位买卖额进行聚合展示。

席位完整性审计发现 Replay 数据存在明确分界：2025-01-02 至 2026-06-16 同时包含营业部和机构席位；从 2026-06-17 起，`top_inst` 只返回“机构专用”，普通营业部席位为零。2026-07-10 的 84 只上榜股票中，59 只有机构记录、25 只没有任何席位记录。因此数据库虽然有 262,770 条席位明细，但近期席位不能视为完整，页面和 API 必须携带覆盖状态。

### 数据批次与状态

每次外部请求产生批次记录，包括 provider、dataset、请求时间、源数据时间、状态、行数、哈希和错误码。状态语义如下：

| 状态 | 含义 | 是否可覆盖有效数据 |
|---|---|---|
| `success` | 契约校验通过并成功入库 | 是 |
| `empty` | 单次请求未返回记录，等待重试 | 否 |
| `unavailable` | 多次确认上游无历史归档 | 否，作为显式覆盖缺口保留 |
| `quarantined` | 行数或字段违反数据契约 | 否 |
| `rate_limited` | 触发上游限频 | 否，延迟重试 |
| `failed` | 网络或服务端故障 | 否，自动重试 |

### 可复现实验

一次实验由策略模板版本、参数、数据版本、代码版本、起止日期共同确定。默认组合规则为等权、最多十只、单股不超过 10%，并预留手续费、印花税、滑点、停牌、涨停不可买与跌停不可卖约束。相同数据与参数必须生成相同指纹和结果。

### 回测与模拟组合的区别

回测一次性重放历史，用于比较策略；模拟组合按真实交易日持续推进，用于暴露订单、现金、持仓和执行问题。模拟组合不等于实盘，不连接券商，也不承诺可交易收益。

## architecture

```text
Tushare Replay（唯一外部数据平台，主动限速约 100 次/分钟）
             │
        Replay Provider
             │
      数据契约 + 批次审计
             │
         PostgreSQL 16
   ┌─────────┼──────────┐
 Research  Portfolio    Ops
   └─────────┼──────────┘
          FastAPI（只读）
             │
      React + TypeScript
```

后端使用 Python 3.12、FastAPI、SQLAlchemy 2 和 Pydantic；前端使用 React 19、TypeScript、Vite、TanStack Query 与 ECharts。任务由 systemd service/timer 执行，不引入当前规模不需要的 Redis、Celery 或 Kubernetes。

数据库按 `market`、`popularity`、`research`、`portfolio`、`ops` 五个 schema 分层。这样既保持 PostgreSQL 是唯一事实来源，也避免采集表、研究结果和业务状态互相污染。

### PostgreSQL 与 Parquet 的职责

PostgreSQL 继续作为事实库，负责唯一约束、事务、增量更新、龙虎榜关联、策略与组合状态以及在线 API。Parquet 不替换数据库，而作为规划中的研究加速层：按月导出日线、人气盘中快照、资金流历史和回测中间结果，通过 Polars/DuckDB 进行大范围扫描。

当前数据规模仍适合 PostgreSQL。引入 Parquet 的触发条件不是“表变大了”，而是重复的跨年全表分析开始显著影响在线 API；届时采用 PostgreSQL → 分区 Parquet 的单向可重建导出，避免形成两个事实来源。

## data-pipeline

### 数据范围

| 数据集 | Replay 接口 | 起始日期 | 入库粒度 |
|---|---|---|---|
| A 股日线 | `daily` | 2025-01-01 | 证券 × 交易日 |
| 东方财富人气 | `dc_hot` | 2025-01-01 | 证券 × 交易日最终榜单 |
| 同花顺热榜 | `ths_hot` | 2025-01-01 | 证券 × 交易日最终榜单 |
| 龙虎榜个股 | `top_list` | 2025-01-01 | 证券 × 原因 × 交易日 |
| 龙虎榜席位 | `top_inst` | 2025-01-01 | 证券 × 席位 × 买卖方向 |
| 个股资金流 | `moneyflow_dc` | 2025-01-01 | 证券 × 交易日 |
| 板块资金流 | `moneyflow_ind_dc` | 2025-01-01 | 行业/概念 × 交易日 |
| 大盘资金流 | `moneyflow_mkt_dc` | 2025-01-01 | 市场 × 交易日 |

资金流接口已完成 Replay 实际验证与历史覆盖审计。2026-07-16 自动增量同步返回 5,935 条个股、1,022 条板块和 1 条大盘汇总；金额字段包含主力净流入、净流入占比及超大单/大单/中单/小单拆分。个股与板块数据已进入每日主链路，并由独立重试任务兜底。

15000 积分接口官方频率上限为每分钟 500 次。最终热榜回补设置至少 0.15 秒请求间隔，理论上限约每分钟 400 次，并通过断点表只重试失败的数据集日期；其他大批量数据仍采用更保守的频率。工作日 22:45 执行每日任务；23:05 再执行独立的双热榜增量同步，失败后每 30 分钟重试，避开盘后榜单尚未生成的时间窗口。

### 质量规则

- 日线单日正常应覆盖不少于 4000 个标的，否则隔离该批次。
- 人气成功批次必须通过字段、日期和最小行数校验。
- 证券代码、日期、金额单位在 Provider 边界标准化，API 不再猜测单位。
- 物化视图只在成功写入后刷新，失败批次不能污染最后有效结果。
- 数据源密钥仅存在服务器环境文件，不进入 Git、API 响应或浏览器资源。

## api-and-ui

公开 API 全部位于 `/api/v1`，仅允许 GET。核心资源包括：

- `/overview`、`/health`、`/data-status`、`/backfill-status`、`/jobs`
- `/popularity/dates`、`/popularity/rankings`：通过 `source=dc_hot|ths_hot` 选择东财或同花顺
- `/popularity/history/{symbol}`：按所选来源返回个股每日最终排名历史
- `/lhb/dates`、`/lhb/records`、`/lhb/seats`、`/lhb/history/{symbol}`
- `/moneyflow/dates`、`/moneyflow/streaks`、`/moneyflow/history/{code}`
- `/strategy-runs`、`/portfolio`

前端按页面懒加载人气图表和龙虎榜模块。查询由 TanStack Query 统一处理缓存、失败和刷新状态；页面不内嵌历史大数据，不使用 iframe。系统状态页以 15 秒周期更新，普通研究数据使用 30 秒缓存。

资金流查询采用严格交易日语义：日期控件只列出数据库内真实存在的交易日；`/moneyflow/streaks` 收到不存在的日期时返回 404，并附带最新可用日期，不再静默回退到此前最近交易日。响应同时返回 `effective_end_date` 与实际参与计算的 `window_dates`，页面以“实际数据截止日”明确展示。

## operations

生产由以下服务组成：

| 单元 | 职责 | 策略 |
|---|---|---|
| `quant-platform-api.service` | FastAPI 只读接口 | 常驻、失败自动拉起 |
| `quant-platform-daily.timer` | 每日增量采集 | 周一至周五 22:45 |
| `quant-platform-popularity-sync.timer` | 东财 / 同花顺热榜增量与失败重试 | 周一至周五 23:05，失败后 30 分钟重试 |
| `quant-platform-moneyflow-sync.timer` | 资金流增量同步 | 周一至周五 23:15；失败后每 30 分钟自动重试，最多持续 6 小时 |
| `quant-platform-backfill.service` | 历史断点回补 | 失败后 30 秒重试 |
| nginx `:8080` | React 静态资源、API 反代、本文档 | gzip、缓存与路由回退 |

运维排查首先看系统状态页，其次检查 `ops.data_batch` 与 `ops.backfill_progress`，最后查看 systemd journal。不得通过直接改业务表来“修复”缺口，应重放对应 Provider 任务并保留批次证据。

资金流同步以日线表的最新交易日为目标，不直接使用服务器自然日，因此周末和跨午夜重试不会请求错误日期。个股、板块或大盘任一接口失败，任务均以失败退出并由 systemd 自动重试；每次运行写入 `ops.job_run`，每个接口批次写入 `ops.data_batch`。系统状态页每 15 秒检查日线、资金流、人气和龙虎榜的完整历史交易日集合，不再只比较最新日期；中间缺口会直接列出具体日期。上游返回的 `trade_date` 必须与请求日期完全相同，否则整批隔离，不允许用旧日数据冒充新日数据。

## roadmap

### P0：当前收尾

- 完成所有可取得历史日期的补数审计，并显式登记 Replay 无归档日期。
- 给人气研究增加来源切换、排名变化、首次入榜和持续时长。
- 给策略实验补充收益、夏普、最大回撤、换手和成交明细接口。
- 给模拟组合补充持仓估值、净值曲线与订单状态。

### P1：研究能力

- 营业部/机构席位历史画像及常见协同上榜关系。
- 人气与龙虎榜事件的次日、五日、二十日收益研究。
- 实验对比、参数网格和基准指数对照。
- 数据字段字典、指标公式和结果导出。

### P2：可靠性

- 数据契约变更告警、延迟告警和失败通知。
